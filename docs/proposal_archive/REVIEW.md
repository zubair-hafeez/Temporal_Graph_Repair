# Critical review of the selected proposal

The recommendation is a plausible first application paper with a meaningful generator contribution. The present evidence supports investing in a bounded baseline study. It does not yet support investing in a full platform rebuild or claiming a publishable result.

## Challenges addressed during review

| Challenge | Change made to the proposal |
| --- | --- |
| Multi-error LLM repair and graph repair already exist. | Removed generic novelty claims. Centered the question on joint identity and participation restoration using generated workflow training, with unfamiliar-process evaluation. |
| “Cross-log transfer” is also already reported. | Required restoration of multi-object structure and application outcomes. Transfer alone is insufficient. |
| A process rule may mistake real behavior for bad data. | Separated genuine execution exceptions from observation corruption; made exception attribution and unnecessary edits explicit evaluation outcomes. |
| Random missing edges are an artificial deployment scenario. | Added executable ingestion faults, such as dropped join batches and stale participant mappings, evaluated separately from random corruption. |
| Identifiers elsewhere in the records reveal masked relationships. | Required corruption of duplicate representations and rebuilding of derived graph edges. |
| An available “real” graph may not encode historical relation validity. | Excluded Angular branch membership from the main evaluation after inspecting the downloaded file. |
| Tuning on clean target examples would undermine the transfer claim. | Assigned BPI 2012 and simulated logs to development, with BPI 2017 and 2019 reserved for final evaluation. Audited target samples and related objects are excluded from the final test. |
| BPI 2012 and 2017 come from the same institution. | Explicitly classified that transfer as a new process/system setting, not a new organization. Purchasing supplies the separate application family. |
| The existing factory could be mistaken for a ready temporal simulator. | Specified reusable engineering patterns and separate new contracts; kept the implementation scope to one workflow family and a research plugin. |

## Risks that experiments must resolve

**Strong simple methods may win.** The temporal-neighbor probe already recovers many of the easier relation holes. A role-aware matcher and a constraint solver are central baselines. If they suffice, the proposed generative model needs a different demonstrated advantage or should be dropped.

**Synthetic transfer may fail.** Generated workflows can teach the wrong regularities. Match the training data budget, hold out mechanisms, and test real-source processes. Adding more generated samples is not a substitute for this test.

**Some histories are unknowable.** Identity and missing participation can be observationally ambiguous. The method must support unresolved outputs. A synthetic generator's hidden answer does not make that answer inferable from the observation.

**The two real applications are still controlled-corruption evaluations.** They support conclusions about restoration of damaged real-source records. Naturally occurring error recovery would require independently verified reference evidence and is not included in the current claim.

**The proposed architecture uses established components.** Publication strength would come from the coherent task, training mechanism, and demonstrated transfer and application benefits. Small gains on one dataset would not justify a broad method claim.

## Recommendation

Proceed with the task contract and strong-baseline stage described in [the proposal](PROPOSAL.md). Keep the final real-process tests sealed. Continue to model development only if the problem remains both recoverable and inadequately solved after leakage removal and baseline strengthening.
